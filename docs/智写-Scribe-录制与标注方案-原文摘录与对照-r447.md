## 一、录制方案（原文摘录）

### 1.1 扩展侧三层：Content Script + Background SW + 消息层（§2.1）

**§2.1.1 Content Script（内容脚本层）** 原文要点：

- **DOM 事件监听**：通过 `addEventListener` 全局监听 `click`、`input`、`change`、`keydown` 等用户交互事件
- **元素定位与特征提取**：当事件触发时，提取目标元素的语义信息（伪代码）：

```javascript
document.addEventListener('click', (e) => {
  const target = e.target;
  const context = {
    tagName: target.tagName,
    innerText: target.innerText?.substring(0, 100),
    id: target.id,
    className: target.className,
    ariaLabel: target.getAttribute('aria-label'),
    xpath: getXPath(target),     // 生成唯一路径用于截图定位
    boundingRect: target.getBoundingClientRect(), // 用于截图裁剪区域计算
    timestamp: Date.now()
  };
  chrome.runtime.sendMessage({ type: 'USER_ACTION', payload: context });
});
```

- **截图触发**：检测到有效用户操作后，通过消息通道通知 Background 层执行截图；**Content Script 自身不直接截图（受 CSP 限制）**
- **URL 变化监听**：通过 `MutationObserver` 或 `popstate`/`hashchange` 事件检测页面跳转，确保 SPA 路由切换不被遗漏
- **输入脱敏**：对 `input[type="password"]` 和敏感字段自动标记为「需脱敏」，截图中以 `***` 替换实际值

**§2.1.2 Background Service Worker（后台服务层）** 原文要点：

- **全局状态管理**：维护录制状态机（`IDLE → RECORDING → PROCESSING → DONE`）
- **截图捕获**：通过 `chrome.tabs.captureVisibleTab()` API 获取当前标签页的可见区域截图，
  **结合 Content Script 传来的 `boundingRect` 进行精准裁剪**
- **事件日志聚合**：接收来自所有标签页的 CS 消息，按时间序列聚合为原始操作日志（Raw Action Log）
- **AI 引擎调度**：录制停止后将原始操作日志发往云端 AI 服务
- **与 Web 端同步**：WebSocket / HTTP 推送到用户 Web 工作区

关键的架构约束原文原话：**「截图触发：检测到有效用户操作后，通过消息通道通知 Background 层执行截图；Content Script 自身不直接截图」**。

### 1.2 桌面端：操作行为捕获 vs 屏幕录制 双模式（§2.2）

**§2.2.1 模式一：操作行为捕获（Operation Capture）——优先路径**

通过 OS 级 API 捕获系统事件：

- **Windows**：`SetWindowsHookEx` 注册全局鼠标/键盘钩子，结合 **UI Automation** API 获取目标控件语义信息（按钮文本、输入框标签等）
- **Mac**：`CGEventTap` 捕获鼠标/键盘事件，结合 **Accessibility API**（`AXUIElement`）获取 UI 元素属性
- **窗口追踪**：监听活动窗口切换，自动关联操作步骤与对应应用程序

**行为捕获的数据结构**（原文 JSON）：

```json
{
  "step_id": 12,
  "timestamp": 1690900000000,
  "action_type": "click",
  "target": {
    "application": "Microsoft Excel",
    "window_title": "Book1 - Excel",
    "element_type": "button",
    "element_text": "Bold",
    "position": { "x": 342, "y": 89 }
  },
  "screenshot_bounds": { "x": 300, "y": 50, "w": 200, "h": 100 }
}
```

**§2.2.2 模式二：屏幕录制兜底（Screen Recording Fallback）**

- 当操作行为捕获**无法获取语义信息**时（老旧 Win32 应用、自定义绘制控件），降级为低码率屏幕录制
- 周期性抓屏（约 2–3 FPS），**帧差分析（Frame Differencing）**，仅保留变化超阈值的帧
- 双模式对比表（原文）：

| 维度 | 操作行为捕获 | 屏幕录制兜底 |
|------|------------|------------|
| 步骤可编辑性 | 高（每步可独立编辑文字/截图） | 低（需额外后处理拆分帧） |
| 资源占用 | CPU < 5%，内存 < 100MB | CPU 10-15%，内存 200-400MB |
| 语义信息丰富度 | 丰富（控件文本、类型、位置） | 无（仅为像素数据） |
| 适用场景 | 标准 Windows/macOS 应用 | 老旧/自定义 UI 应用 |

**§2.2.3 录制容错机制**：

- **无效操作过滤**：自动识别并丢弃误操作（如 50ms 内的连续点击、非功能区域的空白点击）
- **暂停/继续**：用户可随时暂停录制（跳过不需要记录的步骤），恢复后无缝衔接
- **管理员权限处理**：对 Task Manager 等需管理员权限的应用，引导用户以管理员身份运行

### 1.3 录制阶段状态机 + 采集内容（§10.4）

原文状态机（ASCII 原样）：

```
                ┌──────────────┐
        ┌──────→│   IDLE 空闲   │←──────┐
        │       └──────┬───────┘       │
        │              │ Start Capture  │
        │              ▼                │
        │       ┌──────────────┐       │
        │       │  RECORDING    │───────┘
        │       │  录制中        │ Delete / Cancel
        │       └──┬───┬───┬───┘
        │   Pause  │   │   │ Complete Capture
        │          ▼   │   │
        │   ┌──────────┐│   │
        │   │  PAUSED   ││   │
        │   │  暂停中    ││   │
        │   └────┬──────┘│   │
        │  Resume│       │   │
        └────────┘       │   │
                         ▼   ▼
                    ┌──────────────┐
                    │  PROCESSING   │
                    │  AI 生成中    │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   EDITOR      │
                    │   编辑器       │
                    └──────────────┘
```

**录制过程中的数据采集**（原文四条）：

- **鼠标点击**：记录点击坐标、目标元素（DOM 或 OS widget）、对应截图
- **键盘输入**：记录输入内容（明文，编辑时可脱敏）
- **页面/窗口切换**：记录 URL 变化 / 窗口标题变化
- **滚动**：**不单独记录，仅对关键交互点截图**
- **防抖策略**：连续快速点击合并为一个操作；**同一界面停留不动不重复截图**

### 1.4 步骤自动生成四阶段流水线（§4.1 第一层）

**输入**：原始操作日志（Raw Action Log）

```
录制完成
    │  ▼
Phase 1: Capture（捕获）
    - 事件监听器收集 click/input/navigate 事件
    - 每步截图 + boundingRect 坐标
    - 输出：Raw Action Log (JSON)
    │  ▼
Phase 2: Analysis（分析）
    - Computer Vision：识别截图中操作的具体 UI 元素
    - NLP：将原始数据（如 click on element id="login-submit"）
           翻译为自然语言（"Click the 'Log In' button"）
    - 操作意图识别：区分「点击按钮」「输入文本」「选择下拉」「页面跳转」
    │  ▼
Phase 3: Assembly（组装）
    - 自动裁剪截图到操作区域
    - 叠加橙色箭头/高亮标注
    - 拼接步骤描述 + 截图 → 步骤卡片
    │  ▼
Phase 4: Refinement（优化）
    - 过滤无效/重复步骤
    - 合并相邻相似操作（如连续两次点击同一按钮 → 合并为一步）
    - 输出：完整 Scribe 文档
```

报告给出的准确率：**标准 Web 场景步骤描述准确率 > 90%**，复杂操作（拖拽、右键菜单、弹窗交互）**70–80%**。

> ⚠️ 注意 Phase 3 这句「**自动裁剪截图到操作区域**」和 Phase 4 的「**合并相邻相似操作**」——
> 这正是我们「裁图」和「无效点击过滤」两个需求的出处。

### 1.5 编辑器截图编辑层（§2.3.2）

- **步骤编辑器**：左侧边栏步骤列表，支持拖拽排序、合并、删除；主画布展示当前步骤截图与文字
- **截图编辑**：Canvas 渲染截图，**叠加标注层（箭头、高亮框、文字标签）**，支持像素级位置调整
- **富文本编辑**：Markdown 内联编辑，自动保存（Debounce 500ms）
- **版本控制**：每次保存生成版本快照，支持回溯与 Diff

## 二、标注方案（原文摘录）

### 2.1 自动标注（AI 生成，录制完成后自动添加）（§3.3.1）——原文

> **橙色圆形高亮**：在截图中用橙色半透明圆环（`border: 3px solid #F97316; border-radius: 50%`）标记点击位置，这是 Scribe 最标志性的视觉语言
> **自动箭头**：从操作区域边缘指向具体点击/输入位置的橙色箭头，**箭头样式统一（线宽 2px，箭头大小 8px）**
> **输入框高亮**：当步骤涉及输入操作时，用半透明橙色矩形框高亮输入字段区域

### 2.2 手动标注（Pro 用户可编辑）（§3.3.2）——原文

- **移动标注位置**：点击截图上的「铅笔」图标进入编辑模式，可拖拽箭头/高亮到新位置
- **添加文字标签**：在截图上叠加自定义文字说明框
- **添加自定义形状**：矩形、圆形、自由线条
- **替换截图**：上传本地图片替换自动生成的截图

### 2.3 标注样式统一性（§3.3.3）——原文

Pro 团队版支持自定义标注样式（箭头颜色、高亮颜色、字体），全团队保持一致，确保输出文档的视觉品牌统一性。

### 2.4 敏感信息脱敏三级（§3.4）——原文表

| 级别 | 触发方式 | 覆盖范围 | 适用版本 |
|------|---------|---------|---------|
| **自动识别** | AI 自动检测 | 100+ 类 PII/PHI 数据（邮箱、电话、信用卡号、SSN、地址等） | Pro 及以上 |
| **手动脱敏** | 用户在编辑器中点击模糊按钮 | 任意截图区域 | Free 及以上 |
| **强制脱敏** | 管理员设定全局脱敏策略 | 全团队所有文档自动执行 | Enterprise |

技术实现（原文四条）：
1. AI 模型在截图生成时**并行执行 OCR + NER**，检测敏感信息并标记坐标
2. 前端 Canvas 层渲染截图时，对标记区域的像素应用**高斯模糊（`blur radius: 15px`）**
3. 脱敏操作**不可逆**（模糊后的像素数据覆盖原始数据）
4. Enterprise 可配置「强制脱敏策略」

### 2.5 编辑器标注操作矩阵（§10.3 摘录）

| 操作 | 触发方式 | 效果 |
|------|---------|------|
| 编辑文字 | 直接点击步骤描述文字 | 内联编辑，支持富文本 |
| 截图标注 (Pro) | 点击截图上的铅笔图标 | 箭头/矩形框/圆形/文字/自由画笔 |
| 模糊脱敏 (Pro) | 点击模糊工具 | 涂擦敏感区域 |
| 重新截图 | 截图悬停 → Recapture | 用当前界面重新截取该步骤 |
| 添加提示 | 步骤下方 "Add Tip" | 插入额外说明文字块或 GIF |

### 2.6 步骤卡片的视觉结构（§3.2）

```
┌─────────────────────────────┐
│  (1) 蓝色圆形步骤号 ● Step 3 │
│  (2) 步骤标题（AI 自动生成） │  Click the "Save" button
│  (3) 步骤描述（可折叠）      │
│  (4) 全宽截图                │
│  ┌───────────────────────┐ │
│  │   [页面截图，含自动标注] │ │
│  │   → 橙色箭头指向按钮    │ │
│  │   ┌──────────┐        │ │
│  │   │  Save    │ ← 高亮框│ │
│  │   └──────────┘        │ │
│  └───────────────────────┘ │
│  (5) 💡 Tip（可选）         │
└─────────────────────────────┘
```

原文设计细节：**步骤号蓝色圆徽章 `#2563EB`**；**截图默认智能裁剪到操作区域（非全屏）**，用户可切换查看完整截图。

## 四、回答你的那句质疑

> 「这是智写流程的录制方案和标注方案吗？怎么比原来的问题还要大。」

**不是「没抄」，是「抄了一半、而漏掉的那半恰好是用户一眼就能看见的那一半」。**

具体到这次的三张截图：

1. **「还没录制红框就出现」**——这是**生命周期泄漏**：录制态的 UI（`.flowio-hl` 高亮框）没被销毁收口。
   我们把最可信路径查出来了（扩展重载后的**孤儿 CS**：JS 定时器还在跑、`chrome.runtime` 桥已断 ⇒ STOP 永不197到达、`end()` 永不执行），
   并已加「孤儿 CS 自毁」。这类问题智写上不存在，因为它的状态机在 SW 里、页面重载会连带重启；
   我们的问题出在**同一份状态被 CS 与 SW 各持一份**。

2. **「全都没截图、全是＋上传截图」**——**这是本轮真正的主凶，也不是智写口径的问题，是我们自己的迁移事故**：
   r410 把截图改成写 `flowio_shot_<id>` 分片，`lib/shotStore.ts` 是唯一权威；
   但 `src/pages/editor.tsx` 的 `buildStepsFromStorage`（自 v95 起）**还留在读 legacy 单键 `flowio_screenshot_map`**，
   而那个键在 r410 就标注了「⚠️ legacy only（勿写入）」，还会被 `drainLegacyShotMap()` 删掉。
   ⇒ 落库侧明明有 3 张图，面板读 0 张。**本轮已改成走 `readShotShards`，与 SW 侧同一份口径。**

3. **「比原来的问题还要大」**——这个判断是对的，因为原来的问题（图糊、框偏）只影响画质，
   现在这个（全都没有图）影响的是**功能”。而且它掩盖在「复刻智写」这个大目标下，不容易被单独察觉。

**教训（已写进记忆）**：复刻竞品时，**取数口径的迁移必须「写侧 + 读侧」成对改**。
我们这次只改了写侧（SW → 分片），读侧（面板 → legacy 单键）漏了，而读侧漏改**不报错、不崩溃、只是永远拿到空**，
表现恰好就是「用户看到的最严重症状」。

### 5.1 顺带挖出的一个真 bug：裁图没裁

`crop-framing-probe` 的 P5（「裁图像素 = cropRect × 整图」）在本轮**从假绿变成真红**：

```
FAIL  P5 裁图像素 = cropRect × 整图（且确实小于整图）
  步1: 框0.220 整图1000px→裁图1000px 元素占比36%
  步2: 框0.500 整图1000px→裁图1000px 元素占比180%
  步3: 框0.220 整图1000px→裁图1000px 元素占比36%
```

为什么是假绿：探针第 203 行 `if (!s.afterScreenshot) continue;` —— 修之前每步 `afterScreenshot` 都是空的
（正是 r446 那个「面板读不到图」），三次全部 `continue`，`detail` 为空、`pxOk` 保持 `true` ⇒ 判据**一次都没真正跑过**。
修好之后图真的到了面板，循环第一次执行 ⇒ 立刻露出：**`cropScreenshot` 的宽度等于整图宽度，`cropRect` 没生效**。

这与智写 §3.2「**截图默认智能裁剪到操作区域（非全屏）**」是直接对立的一条（上表第 7 行）。
